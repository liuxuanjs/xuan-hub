## 结论

微信生态内的域名随时可能被封。不是"会不会"的问题，是"什么时候"的问题。

核心策略：**授权域名承载非敏感业务，敏感业务用独立域名 + iframe 隔离，后端控制动态切换**。

## 微信域名检测机制

### 检测方式

微信有两种检测手段：

1. **自动检测**：爬虫扫描页面内容、关键词、图片，检查 URL/IP 黑名单
2. **人工检测**：用户举报触发，短时间内举报量达到阈值会进入风险名单

### 常见被封原因

- 域名有历史违规记录
- 流量异常（传播量超过 2000 次会触发审查）
- 诱导分享、裂变传播
- 内容含敏感词
- 同行恶意举报
- 同 IP 下有其他违规域名（连坐）

**关键点**：完全防封是不可能的，只能延长存活周期、降低被封影响。

## 公众号授权域名的限制

在小程序 WebView 中嵌套 H5，如果需要获取用户信息（如微信授权登录），H5 必须在**公众号网页授权域名**下。

### 后台配置

公众号后台 → 设置与开发 → 公众号设置 → 功能设置 → 网页授权域名

### 限制

| 限制项 | 数量 |
|--------|------|
| 网页授权域名 | **最多 2 个** |
| JS 接口安全域名 | 最多 5 个 |
| 修改次数 | 每月有限 |

**只有 2 个授权域名**——这意味着你不能随便换域名。被封了，换备用域名，但备用域名用完了呢？

### 解决思路

1. **授权域名只做授权**：用户进入 → 完成授权 → 跳转到业务域名
2. **授权域名不承载敏感业务**：减少被举报的可能
3. **敏感业务用独立域名**：即使被封，不影响授权流程

## 我们的域名分层架构

### 域名角色划分

```typescript
interface IDomainUsedResponse {
  used: {
    0: string;  // 备用域名
    1: string;  // 授权域名（authDomain）- 配置在公众号后台
    2: string;  // 业务域名（liveDomain）- 承载直播间
    3: string;  // 重定向域名
  };
}
```

| 域名 | 用途 | 是否配置在公众号后台 | 被封影响 |
|------|------|---------------------|----------|
| authDomain | 微信授权、非敏感页面 | 是 | 致命（授权流程中断） |
| liveDomain | 直播间、商品等敏感业务 | 否 | 可快速切换 |

### 为什么这样分

1. **authDomain 必须稳定**：
   - 配置在公众号后台，修改有次数限制
   - 承担授权职责，被封用户就进不来
   - 只放授权页面，尽量减少内容，降低被封风险

2. **liveDomain 可以牺牲**：
   - 不需要配置在公众号后台
   - 通过 iframe 嵌入，用户看不到这个域名
   - 被封了换一个，后端改配置即可

### iframe 隔离架构

```
用户点击分享链接
      ↓
小程序 WebView 加载 authDomain/auth（完成授权）
      ↓
跳转到 authDomain/scene（壳页面）
      ↓
/scene 用 iframe 加载 liveDomain/scene-main（真正内容）
```

```tsx
// authDomain/scene - 只是个壳
const ScenePage = () => {
  const liveDomain = searchParams.get('liveDomain');

  return (
    <iframe
      src={`${liveDomain}/scene-main?${params}`}
      style={{ width: '100%', height: '100%', border: 'none' }}
    />
  );
};
```

**效果**：

- 用户看到的 URL 是 authDomain
- 分享出去的链接是 authDomain
- 真正的业务内容藏在 iframe 里的 liveDomain
- liveDomain 被封？换一个，已分享的链接照样能用

## 动态切换域名的能力

域名保护的关键不是"不被封"，而是"封了能快速恢复"。

### 后端控制域名配置

```typescript
// 小程序启动时获取当前可用域名
const fetchDomainUsed = async () => {
  const res = await request.get<IDomainUsedResponse>('/domain/used');
  return {
    authDomain: res.used[1],
    liveDomain: res.used[2],
  };
};
```

### 切换流程

```
1. 监控发现 liveDomain 被封
2. 运维在后端配置中切换到备用域名
3. 新用户进入时，小程序拿到新域名
4. 旧用户退出再进，也会拿到新域名
5. 无需发版，无需用户更新
```

### 域名池管理

```typescript
// 后端维护多个备用域名
const domainPool = {
  auth: ['auth1.example.com', 'auth2.example.com'],  // 授权域名池（珍贵，数量有限）
  live: ['live1.example.com', 'live2.example.com', 'live3.example.com', ...],  // 业务域名池（可以多备几个）
};
```

## iframe 带来的问题

iframe 保护了域名，但也带来了通信复杂度。

### 问题1：支付链路变长

WebView 里不能支付（见 [WebView里H5能直接支付吗](./WebView里H5能直接支付吗.md)），加上 iframe，链路变成：

```
iframe 商品页 → postMessage → 父页面 → wx.miniProgram.navigateTo → 小程序支付页
```

### 问题2：消息传递层级多

H5 → 小程序的 `wx.miniProgram.postMessage` 在 iframe 里不能直接用：

```typescript
// iframe 内
window.parent.postMessage({ type: 'SHARE_INFO', data }, '*');

// 父页面转发
window.addEventListener('message', (e) => {
  if (e.data?.type === 'SHARE_INFO') {
    wx.miniProgram.postMessage({ data: e.data });
  }
});
```

### 问题3：调试困难

- 三层嵌套：小程序 → WebView → iframe
- 跨域问题：不同域名之间只能通过 postMessage 通信
- 日志分散：要在三个地方看 console

### 消息类型管理

```typescript
// 统一管理，避免混乱
enum IFRAME_MESSAGE_TYPE {
  IFRAME_READY = 'IFRAME_READY',
  LIVE_READY_SHARE = 'LIVE_READY_SHARE',
  PULL_PAY_PAGE = 'PULL_PAY_PAGE',
  CLOSE_LIVE_IFRAME_POPUP = 'CLOSE_LIVE_IFRAME_POPUP',
  RESET_IFRAME_ROUTE = 'RESET_IFRAME_ROUTE',
}
```

## 经验总结

| 原则 | 做法 |
|------|------|
| 授权域名要珍惜 | 只做授权，不放敏感内容 |
| 业务域名可牺牲 | 用 iframe 隔离，方便切换 |
| 动态配置是关键 | 后端控制域名，无需发版 |
| 域名池要充足 | 提前准备备用域名 |
| 监控要到位 | 发现被封及时切换 |

## 这套方案的代价

- 开发复杂度增加（三层通信）
- 调试困难（跨域 + 多层嵌套）
- 性能有损耗（多一层 iframe）
- 域名成本增加（要准备多个备用域名）

但对于直播电商这类高风险业务，这个代价值得。一次域名被封可能损失几十万 GMV，多准备几个域名、多写几行 postMessage 代码，划算。
